## 二、时效性结论：一二三期已解决了文档的哪些痛点

文档写于大改前，以下批评**已被新成果解决或绕过**，核实建议时不要再按文档口径当"现存问题"：

1. **§1-B GmAgent 词法 advice（agent 路径）= 已解决**。一期 agent loop 用 typed 工具（roll_check/apply_effect 等）+ 二期语义路由（SemanticIntentService）取代词法判定。词法残留只在 legacy `plan_turn`，是 legacy 退役的附带清理，**不是独立工程**。

2. **§3-A Module Reader 默认关闭 = 已解决**。2026-06-09 默认翻 ON + 空图谱缓存守卫（重抽自愈），有测试有记忆。文档此条完全过时。

3. **§1-A "多内核挤一条线"对 agent 路径 = 大幅缓解**。`run_gm_turn` 已是干净 typed 状态机，确定性头部四项顺序固定、工具轮循环、两个明确终态。文档把 legacy 长管线当唯一现状是过时的；真正剩余工作是**把 agent 路径升为默认 + 退役 legacy**，而非"从零搭 pipeline"。

4. **§2-A first-pass 容易漏（机制/建卡部分）= 已解决一半**。关键机械数据（机制目录、建卡公式）已是带 get_toc/search/read 工具的真 ReAct evidence 循环 + 强制 source_refs 接地 + 第 2 轮 coverage sweep。文档没区分 onboarding first-pass（仍单遍）与机制/公式编译（已多遍）两层。

5. **§3-E scene_navigator 共享 = 已解决一半**。已抽成 pub、CLI/API 双路径都调（记忆 module-scene-navigation 有据）。剩余只是**输入信号增强**，非"还没接进 runtime"。

6. **§2-C RuleNeed 总线 = 类型层已存在**。`RuleNeedKind` 枚举 + `assist(RuleNeed)` 已建好，文档"建议新增"已部分实现；剩余是**让回合内 kernel 经它发 Need**（贯通问题），不是从头设计。

**仍完全成立（OPEN）**：§1-C 三路径统一、§3-B/C/D 场景块缓存/降级/类型化、§4-隐患1 完整 Need 总线、§4-隐患2 postprocess 竞态、§4-隐患3 文件拆分。

## 三、夜间安全实做清单（低风险高价值，可直接执行）

> 准入：OPEN + night_safe=true + 不动核心回合管线。每项改动前后跑 `cargo check -p <crate>` + 相关单测。

### N1.（P1，低风险，~1 天）§2-B seeded formula 三层 tier 标注
- **现状**：`steward_seeded_formula_pack_json`（`trpg-rule-agent/src/lib.rs:878-927`）给所有 seed 打 `validation_report.status:"ok"`，下游 combat/effect executor 无法区分"种子"与"精确规则"。
- **精确改动**：
  1. 在每条 formula JSON 加 `"tier"` 字段：LLM 抽出且 source-backed = `"exact_executable"`；本函数注入的确定性 seed = `"provisional_seed"`；抽出但缺数值 = `"operational_abstract"`。
  2. seed 注入处（lib.rs:878 起六个 ruleset 分支 + generic 分支 lib.rs:913）统一打 `"tier":"provisional_seed"`。
  3. parser 侧对应 code `source_backed_formula_seeded`（`trpg-parser/src/lib.rs:2287`）同步带 tier。
  4. combat/effect executor 读 tier 加守卫：`provisional_seed` 不当 exact（playability gate 仍放行 operational/seed，但战斗结算遇 seed 走"需查源"分支或 fail-closed 提示）。
- **风险点**：纯加字段 + 读取守卫，不改任何现有算式；`#[serde(default)]` 保证向后兼容旧 pack。
- **验证**：六套规则各跑一次 first-pass，断言 seed 路径 tier=provisional_seed、LLM 抽出路径 tier=exact_executable。

### N2.（P1，低风险，~0.5 天）§3-C SkeletonOnly 当前场景降级块
- **现状**：`scene_node_to_blocks`（`trpg-runtime/src/lib.rs:2248`）对非 DeepExtracted 场景直接 `return vec![]`，切到 SkeletonOnly 且到场深抽失败时 GM 失去"我在哪个场景"。
- **精确改动**：在该函数返回空之前，对 SkeletonOnly 场景产一个轻量 SceneSkeleton 块（复用 `BlockKind::SceneStatic`，scope=Scene，放 DynamicTail/BP3，低 token）：title + summary + page_start/end + known exits（links 标题）+ referenced entity ids + `status=SkeletonOnly` + 指令 `"叙述具体内容前先检索；不要编造 read_aloud/数值"`。
- **风险点**：fail-closed 不编造正文，只投影已知骨架元数据；不动 DeepExtracted 路径。
- **验证**：构造 SkeletonOnly 当前场景，断言产出非空且不含 read_aloud；DeepExtracted 路径行为不变（现有 runtime 测试 lib.rs:3169 区域）。

### N3.（P1，低-中风险，~1 天）§3-B SceneStatic 缓存区可配 PinnedMiddle
- **现状**：`scene_node_to_blocks` 把 DeepExtracted 当前场景产成 SceneStatic 却落 `CacheZone::DynamicTail`（`trpg-runtime/src/lib.rs:2388,2407`），每回合进 BP3，缓存效率差。
- **精确改动**：
  1. 加 env 开关 `TRPG_SCENE_DEEP_BLOCK_CACHE_ZONE`（默认 `dynamic_tail` 保持现状，可设 `pinned_middle`）。
  2. 开关为 pinned_middle 时：DeepExtracted read_aloud/gm_notes/fixed exits → PinnedMiddle + `expires_at_scene`；当前输入/frame/骰子/临时状态保持 DynamicTail。
- **风险点**：默认值保持现状=零行为变更；需确认 `expires_at_scene` 失效语义已实现（grep 确认后再开），否则只加字段不开默认。**若 expires_at_scene 机制不全，本项降级为只加开关+文档、默认关，仍夜间安全。**
- **验证**：开关 pinned_middle 后，只改玩家输入时 pinned_hash 不变、切场景才变；现有缓存稳定性测试（记忆 ux-principles loop 缓存）回归。

### N4.（P2，低风险，~0.5 天）§3-E scene_navigator 输入增强
- **现状**：`scene_navigator`（`trpg-api/src/lib.rs:2055`）主要吃 `full`（GM 叙事），漏判"玩家明说去某地但 GM 叙事含蓄"。
- **精确改动**：给 `scene_navigator` 签名增加 `player_input` 参数（CLI main.rs:1496 / API api/lib.rs:1641 两调用点已有玩家输入在手），prompt 里把 player_input + assistant_output 一起喂语义判定。**保持 fail-closed 默认不动**。切场景成功后写一条 `scene_transition` world event。
- **风险点**：纯增信号不改判定阈值；fail-closed 不动语义不变。关旧场景 gate 留给大重构（涉及 interaction lifecycle，不夜间动）。
- **验证**：构造"玩家明说去 X、GM 叙事含蓄"用例，断言增强后能切、原叙事-only 仍 fail-closed。

### N5.（P2，低风险，按文件逐个，~2-3 天累计）§4-隐患3 大文件拆分
- **现状**：model 6637 / db 4151 / parser 4025 / runtime 3527 / cli 2250 / api 2205 行，违反 ≤400 行护栏。
- **精确改动**：**纯实现文件拆分、public API 不变**（pub use 重导出保持调用方零改动）。优先级：
  - `trpg-runtime/src/lib.rs` → context.rs / session.rs / scene_projection.rs / agent_plan.rs / rule_lookup.rs（已有 chargen.rs/npc_synth.rs 先例）。
  - `trpg-api/src/lib.rs` → routes / sse.rs / turn_postprocess.rs / scene_navigation.rs（scene_navigator 已是 pub，先抽它最安全）。
  - `trpg-parser/src/lib.rs` → rulebook.rs / module.rs / module_blocks.rs / coercion.rs。
- **风险点**：机械搬运，每拆一个文件单独 `cargo check` + `cargo test`，逐文件提交便于回滚。**不要一次大爆破**——按 crate 逐个、每次一个文件。
- **验证**：每步 `cargo check --workspace` 绿、对应 crate 测试绿、`cargo fmt`。

## 四、大架构重构方案（留用户白天拍板）

> 这些动核心回合管线/高风险/跨 crate，不夜间实做。每项给现状/目标/优先级/风险/为何留白天。

### R1. agent 路径升默认 + 退役 legacy（吸收 §1-A/§1-B/§1-C 大半）
- **现状**：三条回合执行器并存。CLI 默认 legacy（`agent` default false），API 完全 legacy。agent 路径 `run_gm_turn` 已可玩但非默认。
- **目标**：① CLI agent 默认翻 ON（A/B 观察期后）；② API 迁到 agent 路径（trpg-api 依赖 trpg-gm，play_turn_sse 改调 run_gm_turn 的流式）；③ legacy `run_turn_once` 退役，词法 `plan_turn` 随之删除。这一步同时消化 §1-B（词法 advice 自然消失）和 §1-C 大半（统一执行器=agent 路径）。
- **优先级**：P1（最高收敛价值）。**风险**：高（动核心、回归面覆盖全部回合）。
- **为何留白天**：要全套 harness e2e 红绿 + 真库三链复测 + A/B 决策，需用户在场拍"何时切默认、是否保留 legacy 作 A/B 一段时间"。是否需要文档建议的声明式 `TurnPipelinePlan`（把 run_gm_turn 的过程式 phases 变 Vec<TurnPhasePlan> 数据）也由用户决定——agent 状态机已够清晰，plan 数据化是锦上添花、非必需。

### R2. 统一 Need 总线（吸收 §2-C/§4-隐患1）
- **现状**：`RuleNeed`/`RuleNeedKind` 类型层已建，但回合内 runtime 走自己的 `auto_search_blocks_for_turn` 绕过 steward；MaterialNeed/SceneNeed/EntityNeed/ParameterNeed 未建。三处独立 search（steward assist / runtime auto-search / materializer）各搜各的。
- **目标**：让回合内 kernel 只发 Need（runtime auto-search 改为发 RuleNeed 经 steward），SearchService 退化为纯 retriever，RuleSteward 当唯一 rule authority；逐步补齐其余 Need 类型。
- **优先级**：P1。**风险**：中-高（改回合检索路径，影响上下文装配/token/缓存）。
- **为何留白天**：涉及"哪些 kernel 何时发 Need、是否同步阻塞 vs 后台"的产品权衡，且与 R1（agent 路径默认）耦合——最好在 R1 落定后基于 agent 路径统一发 Need，避免给 legacy 和 agent 各接一遍。

### R3. RuleClaim/FieldClaim 字段级 verifier（§2-A）
- **现状**：机制/建卡已是 ReAct evidence 抽取，但只到 run 级 confidence + DerivedValue 两态 status，无逐字段 claim ledger。仓内 claim/verifier_status 是 PlayerValueClaim 裁判和学习候选 review，不是规则字段 ledger。
- **目标**：每个抽出字段带 `{claim_id, field_path, value, source_refs, extraction_method, confidence, verifier_status(verified/partial/conflict/unresolved)}`，CharacterOnboardingPack 存"每字段为何可信"，下游 coercion 消费 ledger。
- **优先级**：P2。**风险**：高（新模型 + first-pass 八 subskill 全改携带逐字段 source_ref + 下游消费，触 rule-agent/model/parser 三 crate，估 3-5 天）。
- **为何留白天**：大工程、跨 crate、要重设 schema，需用户确认 ROI（机制/建卡已 source-backed，字段级 ledger 主要收益是审计/冲突检测，优先级低于 R1/R2）。

### R4. ModuleEntity 类型化（§3-D）
- **现状**：ModuleGraph 六类实体全 `Vec<serde_json::Value>`，runtime 消费时字段名/类型不稳定。
- **目标**：引入 `ModuleEntity{id,kind,name,summary,body,content_class,source_refs,page_start/end,extraction_status,data}`，核心字段强类型、`data` 承载自由字段。
- **优先级**：P2。**风险**：中（动 model + 所有读实体处 + reader 提交契约 + 存量 bundle 反序列化兼容）。
- **为何留白天**：需 `#[serde(default)]` + 存量 bundle 迁移策略确认，且与 reader 提交 schema 联动，要用户拍"是否值得现在做 vs 等知识图谱子项目一起"。

### R5. postprocess 临界/重活分层 + high-water mark（§4-隐患2）
- **现状**：agent 路径 verify+finalize 流后同步；API 后台 spawn 有竞态窗口；无 `last_committed_turn_id`/`postprocess_status`/409 防护。
- **目标**：critical postprocess（turn saved/world event/critical patch/便宜的 scene transition）同步完成；heavy（memory/audit/frontier/deep extract）后台；session 加 high-water mark，下一回合发现上回合 critical 未完成则短等或返回 409。
- **优先级**：P2。**风险**：中（动持久化时序 + API 并发语义）。
- **为何留白天**：涉及"用户连发回合时是等待还是拒绝"的产品决策（UX 取舍），必须用户拍。
